### Findings

**L6-01 — The entire cross-tenant isolation suite asserts a mock's configured return value**  
`tests/integration/test_tenant_isolation.py:93-400 (mock setup at 96, 142, 188, 232, 276, 320, 364)` · isolation_break · CONFIRMED  
The empty result the test asserts is the value the test itself stuffed into the mock. No PostgreSQL, no RLS policy, and no real connection participate. The comment attributes the emptiness to RLS; the code attributes it to `AsyncMock(return_value=[])`. Asserting that `set_config` was called proves the dependency emits a statement, not that any policy consumes it.  
*Blast radius:* This is the flagship tenant-isolation gate and it runs on every PR. Drop every RLS policy in db/migrations, or have `get_db_rls_dep` set the wrong GUC, and all 7 tests stay green. The suite that exists specifically because of the Feb-2026 cross-account contamination incident cannot detect that incident recurring.  
*Oracle:* Replace with realdb tests that seed rows for user A under `SET ROLE zenedge_app`, switch `app.current_user_id` to user B, and assert the SELECT returns zero rows — the shape tests/realdb/test_rls_enforcement.py already uses. Keep the mock tests only for the dependency's call contract, and rename them so they stop claiming isolation.

**L6-02 — Endpoint-level cross-tenant tests get their isolation from the fixture factory, not the code**  
`tests/integration/test_tenant_isolation.py:437-607 (Tests 12-16); fixture at tests/conftest.py:391-500` · isolation_break · CONFIRMED  
User A's data is never reachable by user B's request path — not because of any tenant filter, but because the two users were handed two different mock objects and only B's is wired into the app. The endpoint would return `[]` even if it ran `SELECT * FROM logical_trades` with no WHERE clause. Test 16's terminal assertion compares two string literals to each other.  
*Blast radius:* Five endpoint isolation tests (playbook stats, playbook taps, playbook suggestions, trade-by-id executions, demo-user bleed) that gate every merge and verify nothing about tenant scoping. `test_cross_tenant_trade_by_id_returns_404` additionally accepts `(200, 404)`, so both "blocked" and "returned data" pass.  
*Oracle:* Give both users the SAME mock connection and make its `fetch` return user A's rows unconditionally; a correctly-scoped endpoint must then still return nothing for B (because the query carries a user filter or an RLS GUC), and an unscoped one leaks — which is the discriminating experiment. Better: move these to tests/realdb/.

**L6-03 — Cross-tenant streak-metrics test accepts a 500 and guards its only assertion behind an `if`**  
`tests/e2e/local/test_cross_tenant_flow.py:161-181 (assertions at 176 and 179-180)` · isolation_break · CONFIRMED  
Every possible response — success, not-found, and an unhandled server error — satisfies the status assertion. The follow-up assertion is conditioned on the very fact it is meant to establish: if `conn_b.fetchrow` was never called, the `if` is False and the test body executes zero assertions. A test that passes when it makes no assertions cannot fail.  
*Blast radius:* The streak-analysis endpoint's tenant isolation has no gate. The file is `pytestmark = pytest.mark.integration`, so it runs on every PR and reports green regardless of outcome.  
*Oracle:* Drop 500 from the accepted set, and invert the guard: `assert conn_b.fetchrow.called, "endpoint never queried B's connection"` before inspecting the count.

**L6-04 — The `e2e` marker has never gated a merge, and every file behind it is skipped or empty**  
`.github/workflows/test.yml:e2e job: `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`` · trust_break · CONFIRMED  
A tier that runs post-merge cannot gate a merge, and a tier where 100% of tests skip or don't exist verifies nothing even post-merge. The job's Slack alert and auto-issue steps make it *look* like a live safety net on main.  
*Blast radius:* There is no end-to-end verification of any money path — import → group → P&L → report — anywhere in CI. The gap is acknowledged in TEST_PYRAMID_AUDIT_JULY6.md §4.6 as "proposed, not built".  
*Oracle:* Either add `e2e` to the pull_request/merge_group job set with a local-stack variant, or delete the job and stop drawing a box on the pipeline diagram for it. The realdb job is the honest place to put a money-path e2e.

**L6-05 — Autouse `mock_db_pool` in the root conftest patches the DB away for every test in the tree, including tests/realdb/**  
`tests/conftest.py:88-146 (plus mock_sierra_db_pool at 553-620, mock_s3 at 268, mock_openai at 289, mock_slack at 310, mock_telegram at 325)` · trust_break · CONFIRMED  
The failure modes the suite most needs to catch — a query that returns the wrong rows, a constraint violation, an RLS policy that doesn't fire, a transaction that doesn't roll back — are all replaced by a fixed empty answer before any test runs. Every `assert resp.status_code == 200` in the smoke and integration tiers is an assertion about a router's behaviour on an empty mock, not about its query. Inside tests/realdb/, any production code path that goes through `database.get_db()` (rather than the injected `db` fixture) silently receives the mock instead of the real pool, so a realdb test can appear to exercise real SQL while part of the path does not.  
*Blast radius:* Tree-wide: 1,083 smoke tests and ~2,000 integration tests. It is also why L6-01/L6-02 read as plausible — the fixture makes "returns empty" the default outcome, which is exactly the outcome an isolation test wants to see.  
*Oracle:* Scope the autouse mock to tests/unit + tests/smoke, and in tests/realdb/conftest.py add an autouse fixture that explicitly un-patches `database.get_db`/`get_db_connection` so a realdb test that reaches for the global pool gets the real one or a loud error.

**L6-06 — test_tick_sizes locks in a 2x-wrong tick increment for M6E and M6J**  
`tests/unit/utils/test_tick_sizes.py:71 (PAIRS entry), 79-83 (the assertion); source at utils/tick_sizes.py:33-34 and 41-42` · silent_corruption · CONFIRMED  
The premise "micro and full-size instruments must share identical tick sizes" is false for the CME FX micros — the micros are 1/10th notional with a 2x-coarser tick. The test does not merely miss the bug; it encodes it as the specification and will fail the moment someone corrects utils/tick_sizes.py.  
*Blast radius:* Any P&L, excursion, or level computation routed through `utils.tick_sizes.get_tick_size` for M6E or M6J reports double the true tick count, i.e. double the P&L in ticks. The same repo simultaneously holds the right answer in config/instrument_config, so which number a trade gets depends on which module the code path imported.  
*Oracle:* Replace the blanket micro==full parametrization with per-contract literal expectations sourced from the CME spec, and add an explicit negative case: `assert TICK_SIZES["M6E"] != TICK_SIZES["6E"]`.

**L6-07 — Two live tick tables disagree and no test compares them**  
`utils/tick_sizes.py:13-47 vs config/__init__.py:26-58` · silent_corruption · CONFIRMED  
Two sources of truth for the same physical constant, with no consistency assertion, is a divergence that can only be found by a customer noticing their P&L is wrong. The divergence already exists today.  
*Blast radius:* Every instrument, not just the two currently divergent — a future edit to either table silently forks the other. utils/tick_sizes.py is the newer 'single source of truth' (its own docstring says so) yet holds the wrong values.  
*Oracle:* One parametrized test over the union of keys: for every symbol present in both, assert `TICK_SIZES[sym] == instrument_config[sym]["tick_increment"]`, and fail loudly on symbols present in only one.

**L6-08 — Risk-metrics tests assert a max drawdown that is the minimum P&L value, and a Monte Carlo that runs no simulation**  
`tests/unit/services/test_risk_metrics_service.py:266-289 (source at services/risk_metrics_service.py:587-604)` · silent_corruption · CONFIRMED  
Max drawdown is the largest peak-to-trough decline of a cumulative equity curve; for an all-winning series it is 0, never +10. The test name (`..._is_min_value`) states the bug as the intent. `test_large_list_var_indices` recomputes the expected value with the implementation's expression, so it would pass for any index formula. And a function called `calculate_monte_carlo_metrics` that ignores both its confidence level and its simulation count is not doing what its name, its signature, or its callers assume.
